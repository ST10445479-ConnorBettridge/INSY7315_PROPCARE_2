## Defects found and corrected

| Finding | Impact | Correction and regression evidence |
| --- | --- | --- |
| Failed concurrent refresh sent an uncommitted cookie | A losing request could overwrite a valid session cookie and sign the user out | Save the session before setting the cookie. Eight competing refreshes produce one successful rotation; failed rotations set no cookie. |
| Logout depended only on the current refresh-cookie value | A concurrent rotation could prevent the intended session from being revoked | Revoke the authenticated session ID as well as a matching cookie. A stale-cookie logout now invalidates the rotated session. |
| Sign-out ignored network errors | The UI could imply the session ended when the server had not revoked it | Keep the session visible and show a retry message on failure. Browser test simulates HTTP 503. |
| Request screens loaded only the latest 500 records | Older requests could disappear from search/schedules and dashboard counts could be wrong | Server paging and search, complete SQL counts, a separate scheduled-work query and stable page ordering. Verified with 10,000 additional requests. |
| Reports grouped properties and technicians only by name | Distinct records with the same name were merged | Group by identifier plus name. Two same-name properties and technicians remain separate in regression tests. |
| Secondary text failed contrast checks | Dates, breadcrumb text and footer text were difficult to read | Darkened shared colours. Automated WCAG A/AA scans now report no violations across 73 page/viewport states. |
| Unread indicator used an unsupported ARIA label | Screen readers could ignore the notification state | Added an appropriate image role to the labelled indicator. |
| Disabled tenants could not have their tenancy archived | Administration could become stuck after deactivating an account | Allow ending the existing link without requiring an active account; preserve immutable tenancy identity. |
| Database did not enforce the full request-to-tenancy relationship | A direct/imported write could combine an existing unit with the wrong tenant/property | Added a composite foreign key and migration. PostgreSQL rejects a mismatched tenancy even outside the API. |
| Login/profile verification lacked an explicit UTF-8 password limit | Multibyte passwords could exceed bcrypt's input limit despite a character limit | Enforce the same 72-byte limit used when creating passwords. |
| Trusted proxy headers were not processed | HTTPS detection and client-based limiting could be incorrect behind a proxy | Enable forwarded headers for trusted proxies only. Production-mode test verifies HSTS through a trusted local proxy header. |
| Failed photo downloads remained on “Loading” | A missing file or failed request gave no useful feedback | Show an explicit photo-unavailable message. |

## Part 1 alignment and remaining gaps

The 30 functional stories are mapped in [REQUIREMENTS.md](REQUIREMENTS.md). The required React, ASP.NET Core and PostgreSQL stack is in use. Admin login, user/role management, tenant registration and linking, property/category management, technician records and reporting are implemented.

The selected **free deployment preserves the required stack but revises the larger Part 1 cloud design**. [DEPLOYMENT.md](DEPLOYMENT.md) maps each planned component to what is deployed and states the remaining limits. Private object storage and verified database TLS are implemented. React/API hosting shares one Render origin; the database uses a dedicated role/private schema over a public TLS pooler. The application retains its own authentication. A private VPC, separate API gateway, external managed identity and paid uptime monitoring are not claimed. The public endpoint has HSTS and the configured browser security headers; arbitrary forwarded headers remain untrusted.

Outstanding non-functional evidence: first-time tenant completion within three minutes; 99% business-hours uptime (not guaranteed on the chosen free plan); long-duration and cloud load tests; multi-instance operation at the proposed 5,000-property scale; manual WCAG/screen-reader checks; the latest two versions of each target browser; Safari and physical Android devices. Shared object storage is implemented. Email, SMS, malware scanning and external push delivery are not implemented. In-app notifications and admin password reset are implemented.

## Reproduce the checks

```powershell
npm run build
npm test
# Keep npm start running for browser checks.
npm run test:browser
npm run test:browser:edge-cases
npm run test:accessibility
npm run audit:infrastructure
```

The infrastructure audit is opt-in and local-only. It needs `.local/settings.json`, PostgreSQL command-line tools and a database account permitted to create audit databases. It creates uniquely named `propcare_audit_*` databases and ignored backups without dropping or rewriting the application database. `PPC_PG_BIN` can select another PostgreSQL tools directory. Browser tests add clearly named fictional records to the selected demo application. Use `PPC_BASE` to target a separate demo instance and `PPC_CHROME` for a chosen Chromium executable.

Machine-readable results are in ignored `test-results/`; execution logs and backups are in ignored `.local/`. These paths are local evidence, not published credentials or GitHub artefacts. The application remains available at `http://127.0.0.1:5124`.
